stm32mp157d-dk1でのOP-TEE panic (langdale, OP-TEE 3.16.0-stm32mp)
===================================================================

1. 症状
--------
TF-A / OP-TEE / U-Boot / Linuxをmeta-st-stm32mpの"langdale"ブランチの
バージョンに全て揃えたところ(バージョン表はDockerfile冒頭を参照)、
TF-A BL2からBL32(OP-TEE)に制御が渡った直後、OP-TEEが何も出力しないまま
panicするようになった:

    NOTICE:  BL2: Booting BL32
    E/TC:0 0 Panic

file/line/functionの情報もレジスタダンプも無く、これ以外は何も出ない。
Dockerfile記載の素のビルドコマンド(追加フラグ無し)でこの症状が出たため、
最初はボード側のファーム、UART/コンソールの問題、あるいは以前
(langdaleカーネル+scarthgap firmwareを混在させていた時)に見ていた
IWDG2のsecure watchdog問題の再発を疑った。

2. なぜpanicメッセージが空だったか
-----------------------------------
OP-TEEのpanic()マクロ(core/include/kernel/panic.h)は、
CFG_TEE_CORE_DEBUGが定義されている時だけ__FILE__/__LINE__/__func__を
含める:

    #if defined(CFG_TEE_CORE_DEBUG)
    #define __panic(str) __do_panic(__FILE__, __LINE__, __func__, str)
    #else
    #define __panic(str) __do_panic((void *)0, 0, (void *)0, str)
    #endif

そしてcore/arch/arm/plat-stm32mp1/conf.mkは、CFG_WITH_PAGER=y
(STM32MP15ではデフォルト)の場合にCFG_TEE_CORE_DEBUGをデフォルトで
"n"にしている:

    # Default disable some support for pager memory size constraint
    ifeq ($(CFG_WITH_PAGER),y)
    CFG_TEE_CORE_DEBUG ?= n
    ...

つまり「Panic」だけで何も続かないのは、このplatformのデフォルト設定
では正しい・完全な出力であって、途中で切れているわけではなかった。

3. 結果を変えずに発生箇所を特定する
-------------------------------------
最初に試したのは`CFG_TEE_CORE_DEBUG=y DEBUG=1`での再ビルド。これで
発生箇所は分かった:

    E/TC:0 0 Panic at core/arch/arm/mm/tee_pager.c:2036 <tee_pager_init_iv_region>

ただし`CFG_TEE_CORE_DEBUG=y`はコード全体にassert等を追加するため、
常駐必須(non-pageable)な"locked"領域を明確に膨らませる。linker map
で確認したところ、`__init_size`が通常の約12KBから数百KBまで増加して
いた。これだけでTZSRAM(252KB)の予算を食い潰しかねないため、この結果
は「本当のバグ」なのか「診断用フラグ自体が引き起こした副作用」なのか
怪しかった。

より良い方法: `CFG_UNWIND=y`単体。これは`CFG_TEE_CORE_DEBUG`とは
独立していて(core/include/kernel/unwind.h参照)、スタック巻き戻し用
のコードが増えるだけでassertはコード全体に増えない。ビルド:

    make ... CFG_UNWIND=y

これで整形されたメッセージの代わりに、生のアドレス列のcall stackが
出力された:

    E/TC:0 0 Call stack:
    E/TC:0 0  0x2ffc24a9
    E/TC:0 0  0x2ffcae19
    E/TC:0 0  0x3001065d
    E/TC:0 0  0x30021b7f
    E/TC:0 0  0x3002032f
    E/TC:0 0  0x3000f89d
    E/TC:0 0  0x2ffc01a4

ホスト側で、対応する`tee.elf`に対して`addr2line`で解読(コンテナの
out/ディレクトリはbind mountなので、実機を再度触らずに確認できる):

    addr2line -f -C -e out/arm-plat-stm32mp1/core/tee.elf <addr>

    -> tee_pager_init_iv_region   core/arch/arm/mm/tee_pager.c:2038
    -> rwp_init                   core/mm/fobj.c:390
    -> call_initcalls             core/kernel/initcall.c:42
    -> boot_init_primary_late     core/arch/arm/kernel/boot.c:1288

`CFG_TEE_CORE_DEBUG=y`版と同じ発生箇所で、コードサイズへの影響も
最小限だったため、これはdebugフラグの副作用ではなく、フラグに依らない
本物のバグであることが確認できた。

4. 根本原因
-----------
core/mm/fobj.cのrwp_init()(CFG_WITH_PAGER=yの場合、起動時に
無条件で呼ばれる):

    num_pool_pages = tee_mm_sec_ddr.size / SMALL_PAGE_SIZE;
    num_fobj_pages = ROUNDUP(num_pool_pages * sizeof(*rwp_state_base),
                             SMALL_PAGE_SIZE) / SMALL_PAGE_SIZE;
    fobj = rwp_unpaged_iv_alloc(num_fobj_pages);
    ...
    rwp_state_base = (void *)tee_pager_init_iv_region(fobj);

これは、「今ページインしている分だけ」ではなく、secure DDRプール
(tee_mm_sec_ddr)全体のページ数に対して`struct rwp_state`
(iv+AES-GCMタグ、2の冪にpadding済みで32バイト)を1つずつ確保しよう
とする。この確保自体はTZSRAM上にあるtee_mm_vcoreから行われる。

このボードでの数値:
    CFG_TZDRAM_SIZE  = 0x01e00000 = 30MB (plat-stm32mp1/conf.mkのデフォルト)
    30MB ÷ 4KBページ = 7680ページ
    7680 × 32バイト   = 245760バイト(約240KB) ← IVテーブルに必要なサイズ

    CFG_TZSRAM_SIZE   = 0x0003f000 = 252KB(オンチップSRAM全体)
    locked+init領域(素のビルドでtee.mapから実測) 約176KB
    tee_mm_vcoreに残る空き                       約76KB

必要な240KBに対して空きは約76KBしかなく、tee_mm_alloc()が失敗して
tee_pager_init_iv_region()がpanicする。これはこの特定のボード/OP-TEE
バージョンにおける、CFG_TZDRAM_SIZE(30MB)とCFG_TZSRAM_SIZE(252KB)
の構造的な不整合であり、こちらのビルド手順のミスではない。

5. 除外した仮説
---------------
- SRCREVのズレ(meta-st-stm32mpが固定している正確なSRCREVではなく、
  langdaleブランチのHEADをcloneしていること): `git log <固定SRCREV>..HEAD`
  でcore/arch/arm/mm/tee_pager.cとmk/config.mkを確認したがcommit
  0件。conf.mkには関係の薄い(主にSTM32MP13のドライバ有効化)commitが
  少数あるのみ。原因ではない。

- 手動ビルドコマンドが実際のYoctoレシピから逸脱していること:
  meta-st-stm32mp-langdale/recipes-security/optee/
  optee-os-stm32mp-common.incを確認。ST_OPTEE_DEBUG_TRACEはデフォルト
  "0"(st-machine-common-stm32mp.inc)なので、通常ビルドでも
  EXTRA_OEMAKEにCFG_TEE_CORE_DEBUGは追加されない=今回の「素の
  ビルド」と同じ。CFG_TZDRAM_SIZE / CFG_WITH_PAGER /
  CFG_CORE_PAGE_TAG_AND_IVのオーバーライドもmeta層のどこにも無い。
  こちらのビルドは実際のレシピのデフォルトと一致していた。

6. 対処
-------
CFG_CORE_PAGE_TAG_AND_IVはCFG_PAGED_USER_TAをデフォルト値として
継承し、CFG_PAGED_USER_TAはさらにCFG_WITH_PAGERを継承する
(mk/config.mk)。このボードではCFG_WITH_PAGER=yがデフォルトなので、
連動してCFG_CORE_PAGE_TAG_AND_IVも"y"になる。fobj.c側は最初に
これをチェックしている:

    if (!IS_ENABLED(CFG_CORE_PAGE_TAG_AND_IV))
        return TEE_SUCCESS;

明示的に無効化してビルドすると、tee_pager_init_iv_region()自体が
呼ばれなくなる:

    make -j $(nproc) PLATFORM=stm32mp1 \
        CFG_EMBED_DTB_SOURCE_FILE=stm32mp157d-dk1.dts \
        CFG_ARM32_core=y CFG_WITH_LPAE=n \
        CFG_CORE_PAGE_TAG_AND_IV=n

結果: BL32を通過してkernelまで到達するようになった。(kernel側で
別の panic が出ているが、これは無関係な別件として後日調査する。)

トレードオフ: CFG_CORE_PAGE_TAG_AND_IVは、pagerによってTAの
コード/データがDDRに退避される際の整合性タグ(改ざん検知)を提供する
機能。無効化するとこの検証が失われる。暗号化自体は別のpagerロジック
で維持されている想定だが、認証は無くなる。今回のブリングアップ/実験
用途としては許容範囲だが、本来は根本対処(例:CFG_TZDRAM_SIZEを
TZSRAMに収まるサイズまで縮める)を検討すべきで、これは暫定回避策と
して扱うこと。

7. 再利用できる診断テクニック
------------------------------
CFG_TEE_CORE_DEBUG=nのせいでOP-TEEが情報無しでpanicする場合:
  - pager制約のあるplatformでは、まず`CFG_TEE_CORE_DEBUG=y`に
    飛びつかないこと——locked領域を膨らませて本当の失敗を変えて
    しまう/隠してしまう可能性がある。
  - `CFG_UNWIND=y`だけを足す。`CFG_TEE_CORE_DEBUG`とは独立していて
    (core/include/kernel/unwind.h)、コストもずっと小さい。panic時に
    戻りアドレスのraw call stackが得られる。
  - アドレスはホスト側で、対応する`tee.elf`に対して`addr2line`で
    解読する(ARM専用のaddr2lineが無くても、汎用binutilsの
    addr2lineでELF32-littlearmは問題なく読める):
        addr2line -f -C -e out/arm-plat-stm32mp1/core/tee.elf <addr>
  - サイズが怪しいと思ったら、目算ではなくlinker map(tee.map)の
    正式なシンボルで裏付けを取る:
        __init_start / __init_end / __init_size
        __flatmap_unpg_rx_size / __flatmap_unpg_ro_size / __flatmap_unpg_rw_size
    (TZSRAM予算はplat-stm32mp1/conf.mkのCFG_TZSRAM_SIZE)
